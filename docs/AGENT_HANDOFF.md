### T017 — поставщики и прайсы

Поставщики с контактами, условиями оплаты, явно неизвестными или ручными оценками качества/надёжности. Предложения с датами, SKU, упаковкой в базовых единицах, минимумом упаковок, валютой/курсом/источником/датой, доставкой, налоговыми условиями и подтверждением характеристик. Новые прайсы — новые неизменяемые предложения.

Сравнение округляет закупку до целых упаковок и минимума заказа. Неизвестная доставка/налог/курс и неподтверждённые характеристики делают предложение несопоставимым. Иностранный курс вводится с датой и источником; автоматических курсов нет. Налоговый процент берётся из предложения, не из угаданного законодательства.

### T018 — потребность, бюджет, закупочный заказ

Потребность учитывает доступный остаток, резерв, отправленные закупки и складские перемещения в пути, срок, минимум и страховой запас. История использует дни с положительным остатком на конец дня; это ограниченная оценка, не измерение всех внутридневных stockout. При недостатке истории — minimum rule и предупреждения. Отсутствие продаж не объявляется доказательством нулевого спроса.

Бюджет пересчитывает варианты по переданному приоритету и цене; автоматический выбор требует известного срока и оценок качества/надёжности ≥3. Не выбранные позиции остаются с причиной и альтернативами. План пока не сохраняется в БД. В расчёте вариантов доставка на каждую позицию считается отдельно консервативно; в одном реальном заказе одному поставщику — один согласованный delivery charge, распределяемый по стоимости строк.

Состояния закупки: `draft → pending → approved → sent → partial → completed`; отмена возможна до завершения. Одобрение — owner/manager. Purchasing не одобряет сам себя. `sent` — ручная отметка, реальное сообщение не отправляется. Отмена оставляет уже принятый товар и созданный долг.

### T019 — файлы и распознавание

CSV/TSV UTF-8 до 256 КБ, PDF до 5 страниц, PNG/JPEG до 16 Мп, общий максимум файла 5 МБ. Исполняемые форматы и пути в filename запрещены; JSON upload допускает увеличенный лимит только на своём маршруте. Original хранится bytea в БД с org/order и SHA256, скачивание проходит права/branch scope. Не использовать публичные storage URL.

PDF.js извлекает текст; страницы без достаточного текста рендерятся и распознаются Tesseract. PNG/JPEG распознаются локально. Есть предполагаемые строки/количество/цена/сумма; единицы и соответствие SKU требуют ручной проверки. OCR confidence относится к тексту, не к бизнес-достоверности суммы. CSV confidence означает структурный разбор, не подтверждение правильности данных.

Парсер работает в отдельном Node child process: timeout 90 секунд, heap 512 МБ, ограничение количества параллельных запусков на процесс. Это **ещё не durable OCR job**. Ограничение heap не является полноценной OS-песочницей или гарантией лимита native memory. XLSX пока отсутствует. Эти пункты не скрывать при общей приёмке T019.

Проверка дубликатов: file hash по организации, внешний ID по поставщику, номер+поставщик+дата при подтверждении. Повтор того же key возвращает прежний результат; другая попытка дубликата даёт понятную ошибку. Оригинал не перезаписывается исправлениями.

### T020 — сверка и приёмка: начать с проверки остатка

В API есть preview сверки без записи, сохранение исправлений без долга/остатка и отдельное подтверждение. В UI исправления сохраняются, затем показываются расхождения и можно подтвердить их с основанием. Сохраняются версии исправлений и авторы; после подтверждения документ неизменяем. Сравниваются количество, цена, состав и итог; UI сейчас сопоставляет строки с уже заказанными позициями.

Подтверждение создаёт связанное `supplier_obligations.purchase_order_id`; склад не меняется. Платёжный календарь показывает одобренную закупку, затем заменяет её плановую сумму подтверждёнными обязательствами, избегая двойного счёта.

Фактическая приёмка требует одобренной накладной и заказа в sent/partial. Количество вводится **в базовых единицах**. Нельзя превысить остаток документа или заказа. Приход, стоимость, document received, purchase received, новое состояние и audit — одна транзакция. Стоимость частей распределяется накопительным округлением, последний остаток сохраняет исходную сумму до тиына. Повторный запрос и гонка двух SQL-пулов не удваивают приход.

Известный остаток расчёта потребности T018: дневные границы истории сейчас используют `current_date` БД; перед расширением прогноза перевести их в timezone организации и проверить границу суток.

Открытый остаток T020: полноценный UI для лишних/неизвестных строк, замены SKU, решения «отклонить/исправить/создать отдельную закупку», последующая корректировка уже утверждённого документа/долга и расширение независимых concurrency/failure тестов. Сейчас лишняя позиция не может незаметно попасть на склад: приёмка требует строку существующего заказа. Не расширять этот запрет простым снятием проверок.

## Критические технические договорённости

- `Sql.query`, `Database.transaction`; не открывать вложенную transaction на PGlite. `InventoryService.executeInTransaction` и `CommerceService.createInTransaction` нужны для атомарной композиции.
- Внутренний `receiptValueMinor` — точная сумма приходной части накладной. HTTP клиент не может передать его в обычную складскую команду. Не превращать этот аргумент в публичный обход стоимости.
- `sessionAccess` возвращает actor/role/branch. Проверять до чтения, до тяжёлого парсинга и снова в write-транзакции. Finance fields скрывать на сервере.
- Заданный key + другой payload → `IDEMPOTENCY_CONFLICT`. Версии отвечают за гонки различных команд, key — за повтор одной команды. Нужны оба механизма.
- PostgreSQL locks: связанный документ сначала, затем складские/денежные строки в постоянном порядке. Поставщик сериализует подтверждение одинаковой invoice identity по разным заказам.
- Резервы/движения заказа защищены `order_stock_links`; нельзя отдельно выпустить/вернуть их через общий складской API. Для AI и интеграций использовать соответствующую команду заказа.
- `sales_events` — выручка и себестоимость; `money_entries` — деньги. Возврат продаж восстанавливает исходную стоимость выдачи. Нельзя вывести прибыль из остатка кассы.
- Неизвестная стоимость услуги означает `null`, валовая прибыль тогда не вычисляется как будто затрат нет. `expenses_complete:false` остаётся честным ограничением.
- `api(path, method, body)` в клиенте принимает строку метода, не fetch options. HTTP envelope `{data,requestId}` / `{error:{code,requestId}}`.
- `GET organizations/:id` — workspace. Маршрута `/workspace` нет. Складские списки — `/inventory/balances`, не `/stock/balances`.
- `businessDate(date, locale, timezone, withTime?)`; `errorText(code, locale)` принимает строковый код.

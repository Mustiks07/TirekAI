# Локальные модели: речь (T056) и люди на видео (T057)

Проверено 16.10.2026. Обе модели работают **на устройстве** (сервер TirekAI для речи, устройство обработки видео возле камеры), на CPU, без отправки аудио и кадров во внешние сервисы и без их сохранения. Веса скачиваются один раз и в Git не попадают (`.data/models`).

## Речь: как работает

1. Браузер записывает (до 60 с, индикатор, отмена), сам декодирует запись и отправляет **16 кГц моно WAV** (тихая запись нормализуется по пику до 16-битного квантования — без этого Whisper на тихой записи зацикливался, см. TESTING).
2. Сервер (`SPEECH_PROVIDER=local`) передаёт аудио в отдельный долгоживущий процесс `scripts/speech-worker.mjs`; модель загружается один раз (на 4 vCPU ≈ 30 с; при открытии «Помощника» с включённым голосом загрузка начинается заранее), по одной записи за раз, не более трёх ждут (`VOICE_BUSY`), предел 150 с на запрос, через 15 минут простоя процесс выгружается.
3. Для каждого слова берётся вероятность, которую декодер дал его наименее уверенному токену. Неуверенным считается слово с p < 0,5, а суммы, количества и отрицания — при p < 0,9 (`src/domain/speech-review.ts`).
4. Расшифровка попадает только в редактируемое поле вопроса. Если есть неуверенные слова, «Отправить» заблокировано до отметки «Я проверил(а) суммы, количества, названия и отрицания». Голос не вызывает инструменты и не расширяет права: отправка — обычный текстовый вопрос пользователя.

Включение: `npm run speech:model` (≈ 1,3 ГБ, один раз; за прокси — `NODE_USE_ENV_PROXY=1`), затем в `.env.local` `SPEECH_PROVIDER=local`, в «Помощник → Настройки» включить голос. Требования: 4+ ядра, ≈ 2,5 ГБ свободной памяти; на 4 vCPU распознавание идёт примерно в реальном времени (см. замеры ниже).

## Люди на видео: как работает

`npm run video:processor -- … [--detector rfdetr-n|rfdetr-s|dfine-s|motion] [--fps 5]` (по умолчанию rfdetr-n). ffmpeg отдаёт кадры размера входа модели (RGB, кадр растягивается целиком, как при обучении) в память; модель возвращает рамки класса «человек»; почти совпадающие рамки одного человека схлопываются (подавление дублей, IoU > 0,7); ByteTrack связывает рамки в треки; линии, зоны, время в зоне, очереди, полки и рабочие места считает общий модуль `src/server/video/analyzer.ts` — тот же код работает в обработчике и в «Проверке на видео» в приложении. Пока модель считает кадр, чтение из ffmpeg приостанавливается: медленное устройство обрабатывает меньше кадров, но не копит память.

Человек засчитывается («Сейчас видно») с третьего подряд кадра, где его подтвердил трекер; новый трек начинается только с рамки уверенностью ≥ 0,6, продолжается рамками ≥ 0,1 (ByteTrack). Положение человека для линий и зон — центр рамки.

Классический алгоритм остаётся: `--detector motion`. Без модели обработчик **останавливается** с подсказкой (`npm run video:model` или явный `--detector motion`) — тихой подмены нет. Модель записывается в прогон при его начале (миграция 26): прерванный прогон без сводки показывает модель, а старые прогоны без записи — «нет данных о модели» (не «классический режим»). Статус детекторов (experimental/validated) меняется только оценкой разрешённых записей предприятия; по синтетике и открытым роликам validated не ставится.

## Почему сменили модель (16.10.2026)

Пользователь на Windows (встроенная камера, Ryzen 5 5500U) видел «присутствие 0», стоя перед камерой, при 275 обработанных кадрах и 0 непригодных. Разбор по звеньям «кадр → вход модели → рамки и оценки → пороги → трекер → зона → события → экран»:

1. **Вход модели проверен**: размер 640×640, порядок RGB, масштаб 1/255 без нормализации — совпадает с `preprocessor_config.json`; та же картинка через эталонную обработку transformers.js даёт те же оценки (±0,06 из-за другой интерполяции). Класс 0 = person подтверждён `config.json`.
2. **Звено, которое ломается, — сами веса D-FINE-N в этой выгрузке.** На реальных кадрах: рабочий в оранжевом жилете крупным планом — «backpack 0,33», человека нет совсем; COCO val 139 (человек в комнате) — не найден; групповое фото — максимум 0,57. На тех же кадрах D-FINE-S даёт 0,74–0,95, RF-DETR Nano — 0,94–0,99. Порог нового трека 0,6, поэтому трек человека, вероятнее всего, не начинался вовсе. Подтвердить это на камере пользователя можно только у него: `npm run video:check -- --webcam "video=HD User Facing"` (docs/CAMERA_WINDOWS.md) печатает лучшую оценку человека и звено, на котором теряется счёт. Кадры COCO val2017 использованы только для этой сверки (условия Flickr у каждого снимка), в репозиторий не добавлялись.
3. На видео с потолочной камерой (`people-detection.mp4`, Intel, CC BY 4.0) прежняя D-FINE-N за 50 с не насчитала **ни одного** человека — тот же симптом, что у пользователя. RF-DETR Nano: 7 из 7 людей, максимум 3 одновременно.
4. Ещё одно расхождение экрана: «Зоны: в среднем видно» было средним за 10 с и за час, а не текущим числом. Теперь на главном экране — число людей на последнем обработанном кадре (только при свежем сигнале), среднее за час — в «Качество и проверка».

Порог не снижался: при работающей модели люди получают 0,94–0,99.

Загрузка модели — около 30 с. Короткая фраза распознаётся ~8–9 с: модель всегда обрабатывает 30-секундное окно. Казахский заметно хуже русского; TTS-голос казахского неестественен и занижает результат, поэтому нужны живые записи сотрудников. Пометки не ловят все ошибки: они дополняют, а не заменяют чтение расшифровки перед отправкой.

На Ryzen 5 5500U (6 ядер/12 потоков) ожидается не медленнее; если обработка не успевает, ffmpeg просто отдаёт меньше кадров (обратное давление), фактическая частота видна на экране как «поступает N кадр/с».

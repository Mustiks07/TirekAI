# Безопасность основания

Реализовано: серверные memberships; параметризованный SQL; allowlist ролей и профилей; branch scoping; составные FK; транзакции; случайные 256-bit session/invite токены и хранение только hash; scrypt N=32768,r=8,p=1; HttpOnly/SameSite=Lax cookies; Secure при HTTPS; проверка Origin для мутаций; ограничение размера JSON; лимит 8 попыток входа за 15 минут на email; 12-часовые сессии; 48-часовые одноразовые приглашения; запрет выдачи owner через invite; повторная проверка создателя; отзыв всех сессий исключённого сотрудника.

Логи ошибок содержат только код и requestId. Аудит содержит тип операции и роль, без паролей, токенов, почтовых адресов и тел запросов. Приглашение возвращается создателю один раз; фрагмент URL не отправляется серверу при переходе. Email остаётся видимым самому участнику и лицам с правом чтения команды.

Локальная саморегистрация подтверждает только владение сессией, не email. Поэтому режим предназначен исключительно для синтетических данных, слушает loopback и явно помечен. Внешняя саморегистрация закрыта. Это не готовая identity-система для реальных организаций.

Импорт: проверка сессии/роли/филиала перед парсингом и повторно в write-транзакции. UTF-8, ограничение байт/строк/размера записи, фиксированные поля; содержимое не исполняется и отображается React как текст. Клиенты уникальны внутри организации/филиала/источника. Worker не доверяет старому cookie: перед каждой порцией проверяет сохранённого инициатора и текущий membership/branch. Исключение до выполнения переводит задание в cancelled; повтор собственником явно меняет инициатора. После обычного logout ранее подтверждённое задание может завершиться, если членство остаётся активным.

Локальный worker bridge: 256-bit секрет в памяти supervisor, constant-time сравнение, закрыт вне LOCAL_PREVIEW+LOCAL_DATABASE, hostname loopback. Пользовательские cookies не дают доступ. Внешний PostgreSQL-worker использует SQL напрямую. Сырые CSV и контакты сохраняются только в синтетической БД, в лог/аудит не попадают. До живых данных нужны политика retention, удаления/экспорта, квоты импорта и роли БД.

До живого запуска: доверенный identity-провайдер или подтверждение email, восстановление аккаунта, MFA owner/admin, независимая проверка криптографии и сессий, распределённые лимиты/IP, срок хранения и очистка auth_limits, CSP, приглашения по проверенному каналу, RLS/DB grants, пагинация прежних списков, нагрузка, резервное копирование и восстановление. Права финансовых полей, export/AI/realtime проверяются при появлении этих поверхностей. Текущие тесты не подтверждают ещё не реализованные пути.

Администратор платформы не реализован. UI не предоставляет административного обхода чужих memberships. Камера заблокирована Permissions-Policy. Микрофон разрешён только для собственного origin (T028) и запрашивается после явного нажатия «Записать вопрос»; запись ограничена 60 с, треки освобождаются при остановке, отмене и уходе со страницы, аудио не сохраняется.

Каталог/склад: скрытие финансовых полей выполняется SQL-проекцией на сервере, а не только UI. Sales/observer не получают purchase_price/value_minor. Составные FK изолируют документы по организации; склады проверяются по branch scope. Идемпотентность не обходит актуальную авторизацию. Недоступный склад/товар возвращает 404, запрещённая роль — 403. Формы не принимают actor, стоимость выдачи или время проведения от клиента. Прошлые движения не имеют API редактирования/удаления.

PWA: кешируются только offline HTML и три иконки, все пользователи получают одинаковую публичную оболочку. API/авторизованные страницы не кешируются, сторонних запросов, push и background sync нет. Тест Cache Storage подтверждает allowlist после обращения к session API. Это не режим офлайн-доступа к бизнес-данным. Нативная установка и реальный многопользовательский security-аудит остаются отдельными проверками.

`.data`, `.local`, `.env`, логи и результаты тестовых трасс исключены из git. Они также исключены из server tracing. Fixtures используют уникальные случайные пароли, записанные в игнорируемый локальный файл. Не копировать этот файл в артефакты или переписку.


Заказы/финансы: каждая команда проверяет текущие membership и branch scope. Клиент, склад и денежный счёт документа должны принадлежать нужному филиалу. Sales может оформлять заказ/исполнение, но не финансовые записи и не чтение стоимости. Даже повтор idempotency key проходит авторизацию. Подмена ID в возврате ограничена организацией и исходным заказом/исполнением; избыточный возврат откатывается. Заказные движения нельзя возвращать через общий stock API. Банковские запросы, письма и сообщения не отправляются.

Суммы ограничены схемами и SQL CHECK; отрицательные деньги/остатки не допускаются. Переводы блокируют счета в одном порядке. Документы/журнал не имеют API удаления. Календарь читает до 5000 документов и 365 дней, не пишет события/деньги; неполный результат вместо молчаливого обрезания отклоняется. Полный security/load audit и независимая проверка финансового модуля остаются перед живым запуском.

## Документы и PDF

Доступ к оригиналам и CRM PDF проверяется по организации/филиалу; ответы не кешируются публично. OCR выполняется дочерним процессом без app credentials в окружении, с timeout и ограничениями файла/страниц/изображения/вывода. Модели языка поставляются npm-зависимостями, распознавание не требует внешнего API. Это не полноценная OS-песочница и не durable queue; native memory и защита от вредоносных parser inputs требуют отдельной production приёмки. PDF создаётся из авторизованного snapshot предложения и встроенного лицензированного шрифта.

## T020–T030

- Все новые команды: сессия или `InternalActor` с повторной проверкой членства; организация/филиал в запросах; повтор ключа не обходит права. Задачи видны исполнителю, автору, заместителю после эскалации и управляющим своей области. Проверку выполняет другое лицо с правом tasks:verify.
- Ситуации показываются только ролям, которые могут читать исходные данные правила (например, долги — finance:read). Знания: черновики только редакторам, поиск — только опубликованные версии своей организации, филиала и роли.
- Согласование: запрет самосогласования, лимиты ролей, делегирование не превышает полномочий делегирующего и перепроверяется при исполнении. Автоматизации и AI только предлагают закупку; согласует человек.
- AI: ключ только в окружении сервера, не попадает в клиентский бандл и логи; разговоры приватны; инструменты используют права пользователя; результаты инструментов и документы передаются модели как данные; нет инструментов SQL/shell/HTTP/согласования/оплаты. Бюджет токенов и выключатель у собственника.
- Интеграции: токен МойСклад шифруется AES-256-GCM ключом `INTEGRATION_ENCRYPTION_KEY` (32 байта base64) и не возвращается API; без ключа реквизиты не сохраняются. Отключение стирает реквизиты. Входящий вебхук: случайный токен в пути (хранится хеш, сравнение постоянного времени), лимит 64 КБ, дедупликация requestId, ссылки из тела события не запрашиваются. Исходящие запросы только на официальный хост, без редиректов, с таймаутами.
- Загрузки задач и знаний: проверка расширения и сигнатуры (PNG/JPEG/PDF, UTF-8 текст без управляющих символов), лимиты размера, хранение в БД с проверкой доступа при скачивании.
- Не проверено: независимый аудит prompt injection на живой модели, нагрузка, ротация ключа шифрования (сейчас требует повторного ввода токена).

## T031–T040

- Входящие вебхуки Битрикс24 и Telegram: секрет в пути (хранится хеш) и второй секрет (application_token / заголовок `X-Telegram-Bot-Api-Secret-Token`) проверяются до сохранения события; лимит тела, дедупликация. Исходящие запросы: только HTTPS к публичным хостам (1С — проверка DNS на частные адреса), без редиректов, с таймаутами.
- Сообщения клиентам: исходящие Telegram выключены до разрешения владельца; согласие и привязанный чат проверяются при постановке и повторно при отправке; `/stop` отзывает согласие. Клиенты из Битрикс24/1С/Kaspi приходят без согласий. Покупатели Kaspi сводятся к одному клиенту канала; имя и телефон остаются в заказе канала.
- Записи во внешние системы (статус Kaspi, приёмка МойСклад) выключены по умолчанию, включаются владельцем и выполняются явным действием один раз; неизвестный результат не повторяется автоматически.
- Деньги из внешних отчётов (выписка банка, отчёт Kaspi) не проводятся автоматически: человек выбирает действие, суммы проверяются арифметически, одна строка проводится один раз; проводка — через сервис денег с правами `finance:write`.
- Видео: устройство аутентифицируется токеном источника (хеш в БД); принимаются только агрегированные события, кадры и учётные данные камеры в приложение не передаются, `raw_storage` запрещён ограничением БД.
- Продвижение: себестоимость и маржа скрыты без `inventory:cost`; согласование не автором версии; разрешение ниже порога — только владелец с причиной; изображения проверяются по сигнатуре PNG/JPEG.

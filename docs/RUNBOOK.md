# Запуск и остановка

## Локальный процесс

Команда `npm run dev` или, после `npm run build`, `npm run preview` запускает web на `http://127.0.0.1:3000` и один worker импорта. Данные находятся в `.data/local`. PGlite живёт внутри web-процесса. Worker раз в секунду вызывает защищённый loopback-мост, который обрабатывает до 25 строк за вызов. Это не отдельная служба БД. Камеры и AI не запускаются. Worker печатает назначение/PID; секрет генерируется supervisor только в памяти.

Остановка web и worker: Ctrl+C в терминале запуска. Завершение любого дочернего процесса останавливает второй. Не завершать все процессы Node на компьютере и не удалять базу ради остановки. Если терминал потерян, найти PID конкретного порта через `Get-NetTCPConnection -LocalPort 3000 -State Listen`, проверить командную строку и путь процесса, затем остановить только процессы этого запуска (включая worker из лога).

Проверка ожидания очереди: задать `$env:WORKER_DISABLED='1'` перед локальным запуском; подтвердить импорт, остановить сервер, удалить эту переменную и запустить снова. Очередь продолжится. После аварии lease живёт до 30 секунд. `failed`/`cancelled` требуют кнопки повтора сотрудником с правами. Успешные порции повторно не записываются. Heartbeat старше 10 секунд показывает отсутствие обработчика.

Для выделенного PostgreSQL сначала `npm run db:migrate` одним исполнителем, затем web и отдельный `npm run worker` с DATABASE_URL. Worker не запускает миграции. Конкурентная обработка проверена с двумя worker-объектами через независимые PostgreSQL-пулы; отдельные OS-workers под нагрузкой ещё не проверены. Потребление при локальном простое: один Node-worker с опросом раз в секунду и PGlite внутри web; измерения CPU/RAM/p95 под нагрузкой ещё не выполнены.

Проверки Playwright временно занимают порт 3100 и отдельный `.data/e2e-*`. Они не используют `.data/local`. Нельзя одновременно открывать одну файловую базу в web и seed. Local lock показывает занятый PID; после аварии мёртвый PID очищается при следующем открытии. Если PID занят другим процессом, сначала проверить принадлежность, не удалять lock вслепую.

## Изолированные проверки PostgreSQL

`npm run test:postgres` требует установленного PostgreSQL. По умолчанию бинарники ищутся в `C:/Program Files/PostgreSQL/18/bin` (Windows) или `/usr/lib/postgresql/18/bin` (Linux); `PG_BIN` переопределяет каталог. На этом стенде проверен Windows/PostgreSQL 18.2; Linux-запуск отдельно не проверен, его следует выполнять обычным пользователем.

Runner создаёт `.data/postgres-tests-*`, случайный пароль SCRAM и свободный порт только на 127.0.0.1. Существующие базы, службы и DATABASE_URL не используются. Пароль передаётся initdb через временный файл в `.local`, удаляемый сразу после инициализации; затем только через окружение тестового процесса. Не публиковать дампы окружения. Логи сервера и синтетическая база сохраняются в игнорируемом каталоге.

На время команды работают отдельный сервер PostgreSQL (до 30 соединений), два SQL-пула до 10 соединений и Vitest. После успеха, ошибки теста или обычного Ctrl+C runner вызывает pg_ctl fast stop именно для своего каталога. При принудительном завершении самого runner автоматическая остановка не гарантируется: проверить путь `-D` процесса и выполнить `pg_ctl -D <точный каталог .data/postgres-tests-...> -m fast -w stop`. Не останавливать системную службу и не удалять PID-файлы работающего сервера. pg_ctl запускается со скрытым окном; в Windows использует ограниченный токен.

## Заказы и финансы

Миграция 4 применяется при следующем локальном старте; для PostgreSQL — штатной db:migrate перед приложением. Начальные данные прежних миграций не переписываются. Новые функции не запускают дополнительных workers, служб, банковских подключений или плановых платежей. Браузер обновляет списки после действий и по кнопке; realtime пока отсутствует.

При VERSION_CONFLICT обновить карточку и сверить последнее действие. При сетевой ошибке проверить журнал/заказ перед новым вводом: открытая форма сохраняет ключ повтора для неизменённого запроса, но после перезагрузки браузера ключ не восстанавливается. Возврат товара делается в заказе, возврат денег — отдельно в финансах. Нельзя менять SQL-журнал для исправления цифр. Сторно прочих ручных расходов ещё не реализовано.

## Ошибки

- `INTERNAL_ERROR` с requestId: проверить окружение, занятый каталог и версии миграций. Приложение не печатает в лог SQL, тела запросов или секреты.
- `UNAUTHENTICATED`: истёкшая/отозванная сессия, войти снова.
- `FORBIDDEN`: проверить организацию, роль и филиал; клиентский organization_id не предоставляет доступ.
- `INVALID_INVITATION`: проверить email, срок, отзыв/перевыпуск. Попросить собственника создать новую ссылку.
- `RATE_LIMIT`: ждать завершения 15-минутного окна. Не удалять ограничения для обхода поставщика.
- `Migration was modified`: вернуть прежний применённый SQL и добавить новую миграцию, не менять checksum вручную.

## PWA

Service worker работает в браузере только после production preview, без отдельного OS-процесса. В dev новый worker не регистрируется. Для проверки чистого dev после preview при необходимости удалить регистрацию текущего localhost-origin через DevTools → Application → Service Workers; это не удаляет серверную PGlite БД. Cache Storage `basqaru-public-v1` содержит только публичные иконки/offline HTML. Не очищать все данные других origin.

После обновления закрыть/сохранить формы и использовать кнопку обновления приложения. Нативная установка выполняется только штатным браузерным подтверждением. Офлайн-баннер предупреждает, что перед повтором команды надо проверить результат после подключения; автоматического replay нет.

## T020–T030: worker, ключи и проверки

Worker (локально через `/api/internal/worker`, для PostgreSQL — `npm run worker`) на каждом тике: импорт, периодические задачи, эскалация, истечение предложений, обнаружение ситуаций (не чаще раза в 5 минут на организацию), автоматизации (outbox → исполнения), синхронизация МойСклад (не чаще раза в 15 минут) и входящие вебхуки. Повтор тика и перезапуск не дублируют результат. Ручной разбор автоматизаций — раздел «Автоматизации», журнал; повтор — кнопка «Повторить».

Переменные (только сервер, не в git): `ANTHROPIC_API_KEY`, `ASSISTANT_MODEL`, `INTEGRATION_ENCRYPTION_KEY` (32 байта base64; смена ключа делает сохранённые токены нечитаемыми — после смены токен вводится заново). Без них функции честно показывают not_configured, остальное приложение работает. Живой eval помощника: `npm run eval:assistant` с ключом в `.env.local` или окружении (расходует токены; запускать только с разрешения владельца бюджета), отчёт в `docs/evidence/assistant-eval-YYYY-MM-DD.json`.

## T031–T040: подключения, видео, каналы

Worker дополнительно вызывает `runConnectors`: Битрикс24, 1С, Kaspi (не чаще раза в 15 минут на подключение), входящие события Битрикс24/Telegram и очередь исходящих Telegram. Все подключения настраивает владелец на странице «Подключения»; реквизиты шифруются `INTEGRATION_ENCRYPTION_KEY`.

- Telegram: токен бота → «Проверить» → «Зарегистрировать вебхук» (нужен публичный HTTPS-адрес приложения) → «Разрешить исходящие». Клиент привязывается кодом `/start <код>` (выдаёт сотрудник, 7 дней). Таймаут при отправке = «результат неизвестен», повтор вручную после проверки в Telegram.
- Kaspi: токен из кабинета продавца, филиал и склад. Заказы читаются автоматически; перенос, подтверждение в Kaspi, выдача, отчёт о выплате и возврат — на странице «Продажи», панель «Заказы Kaspi». Смена статусов в Kaspi включается владельцем отдельно. Комиссия и выплата вводятся из отчёта Kaspi.
- Банк: на странице «Финансы» привязать IBAN к счёту и загрузить файл 1CClientBankExchange; каждая строка проводится, сопоставляется или пропускается человеком.
- Видео: обработка идёт отдельным процессом на устройстве в сети камеры, нужен ffmpeg в PATH (или `FFMPEG_PATH`). Владелец создаёт источник и получает токен устройства (показывается один раз). Запуск: `VIDEO_DEVICE_TOKEN=… npm run video:processor -- --server https://<приложение> --source <id> --file clip.mp4` (или `--rtsp` с `VIDEO_RTSP_URL`, `--webcam <устройство>`). Учётные данные камеры остаются на устройстве; кадры не отправляются. Оценка: `npm run eval:video`.
- Продвижение: PDF-материалы скачиваются со страницы «Продвижение» после согласования; рассылка — только Telegram и только клиентам с согласием. Генератор изображений, e-mail/SMS и рекламные кабинеты не подключены.

Проверки 15.10.2026: временный кластер PostgreSQL и серверы e2e остановлены после прогона.

## T046–T050: новые процессы и восстановление

Строительство: создайте каталог материалов и итоговую услугу, заказчика и поставщиков/подрядчиков. Объект/смета → другой руководитель согласует → закупка объекта → кнопка «Открыть закупку и приёмку» → обычное согласование/накладная/фактическая приёмка → выдача на объект → запись работ → второй проверяющий → приёмка объекта → заказ/оплата. Допобъём оформляется новой сметой, снова требует согласования. Подтверждение работ создаёт обязательство подрядчику в финансах, не переводит деньги. Бюджет учитывает обязательства закупок и работы; фактические материалы считаются отдельно, повторно к сумме закупки не прибавляются.

Клиника: направление — услуга каталога; ресурс специалист и кабинет с графиком; административная заявка с минимальным контактом → запись/перенос → visited → счёт → обычная оплата. No-show/cancelled не создают счёт. В общих финансах клиент обезличен; не заменяйте его именем пациента и не вводите медицинские решения в административные поля.

Результаты: выберите филиал и даты создания заказов. Выручка и деньги показываются отдельно, ссылки раскрывают исходные события; подготовка публикации не является её доставкой или выручкой. До исполнения можно зафиксировать прогноз, а до утверждения накладной — альтернативную цену закупки с одинаковым объёмом и условиями. Прогноз не является доказательством экономического эффекта.

При потере ответа повторять ровно тот же запрос и key; изменение параметров требует нового намерения, а не обхода конфликта. Если результат внешней отправки unknown, сначала сверить его у провайдера: новый key не разрешает безопасно дублировать сообщение/приёмку. При локальном аварийном завершении сначала подтвердить остановку собственного процесса, затем запустить обычный preview: stale lock обрабатывается только при отсутствии процесса-владельца. Не трогать системный PostgreSQL 18.

Проверка восстановления: npm test включает tests/failure-recovery.test.ts (свой дочерний OS-процесс, crash внутри транзакции выдачи, повтор после restart, exit после commit оплаты), database-recovery.test.ts (ошибка конфигурации/контрольной суммы, release своего lock/handle, восстановление), прежний restart.test.ts (импорт) и automation/adapter отказные сценарии. Синтетические кластеры остаются в игнорируемом .data для диагностики. Это не проверка полной утраты диска и не backup/restore production: этот объём относится к T053.

## T053: развёртывание, резервные копии, восстановление и эксплуатация

Проверено на изолированном PostgreSQL 16 в облачном Linux-контейнере. Это инструкция и подтверждённые учения на тестовом стенде; production-размещение, регион хранения и юридическая проверка обработки персональных данных в Казахстане не выполнялись (решение заказчика перед запуском).

### Развёртывание (PostgreSQL)

1. Сервер PostgreSQL 16+ в выбранном регионе; отдельная база и роль приложения (владелец схемы для миграций). Для эксплуатации рекомендуется две роли: `migrator` (DDL, только на время `db:migrate`) и `app` (DML). Сетевой доступ только из приложения/worker.
2. Окружение web и worker (через секреты платформы, не в git): `DATABASE_URL`, `APP_ORIGIN` (публичный HTTPS-адрес), `INTEGRATION_ENCRYPTION_KEY`, при необходимости `ANTHROPIC_API_KEY`, `DATABASE_POOL_MAX` (процессы × пул < `max_connections`). Пустой `LOCAL_PREVIEW`/`LOCAL_DATABASE`.
3. `npm ci && npm run build`.
4. Перед каждым релизом: `npm run db:backup`, затем `npm run db:migrate -- --plan` (показывает применённые/ожидающие; отказ, если выпущенный SQL изменён или база новее кода), затем `npm run db:migrate` одним исполнителем. Миграции атомарны по версии и сериализуются advisory-блокировкой: параллельный запуск двух экземпляров проверен (tests/postgres.integration.ts).
5. Запуск: `npm start` (web, за обратным прокси с TLS) и отдельный процесс `npm run worker`. Проверка: `GET /api/health` → 200 и `{"status":"ok","schema":"ok","worker":"ok"}`; 503 при недоступной БД или несовпадении схемы. Без авторизации, без данных организаций.

### План отката

Миграции только вперёд. Откат релиза: остановить web/worker новой версии → восстановить резервную копию, снятую перед миграцией, в **новую** пустую базу (`npm run db:restore`) → направить предыдущую версию приложения на неё → проверить `/api/health`. Изменения, внесённые после копии, переносятся вручную по журналу аудита. Повреждённую базу не перезаписывать: она нужна для разбора.

### Резервные копии

`npm run db:backup [-- --out <каталог>]` с `DATABASE_URL`: `pg_dump` (custom) из экспортированного снимка транзакции и манифест `*.manifest.json` с версиями миграций и отпечатком каждой таблицы (число строк + md5 всех строк) из того же снимка. С `BACKUP_ENCRYPTION_KEY` (32 байта base64) файл шифруется AES-256-GCM; ключ хранить отдельно от копий. Пароль БД передаётся утилитам через окружение, а не в аргументах. Расписание (пример cron): ежедневно `0 2 * * *` + перед каждым релизом; хранить 7 ежедневных и 4 еженедельных копии вне сервера БД; раз в месяц выполнять учения восстановления.

### Восстановление

`RESTORE_DATABASE_URL=<пустая база> npm run db:restore -- --file <копия> --confirm`. Проверяется sha256 файла, при шифровании — ключ (неверный ключ и изменённый файл отклоняются), целевая база обязана быть пустой (непустая отклоняется: данные не перезаписываются), `pg_restore --single-transaction --exit-on-error`, затем сверка каждой таблицы с манифестом. Учения: `npm run test:restore` — изолированный кластер, копия под нагрузкой записи, отказы, удаление исходной базы, восстановление зашифрованной копии, вход, равенство финансовой сводки, расшифровка реквизитов интеграции и новая операция. Результат: docs/evidence/restore-drill-2026-10-15.json.

Локальный предпросмотр (PGlite, только синтетика): остановить `npm run dev`/`preview` и скопировать `.data/local` целиком; восстановление — вернуть каталог при остановленном приложении. Это не процедура production.

### Сроки хранения, обезличивание, экспорт

- `npm run ops:retention` — сухой прогон (что будет удалено), `-- --apply` — применить. Только технические данные: истёкшие сессии и счётчики входа, тела обработанных входящих событий старше N дней (строка остаётся для защиты от дублей), журналы синхронизаций, прочитанные уведомления, использованные коды привязки, старые тестовые прогоны правил и прогоны ситуаций. Сроки — `RETENTION_*_DAYS` (.env.example). Аудит, журналы склада и денег, документы, outbox и задачи не удаляются. Рекомендуется ежедневно после резервной копии.
- Обезличивание по запросу субъекта (только владелец): `POST organizations/:id/privacy/customers/:customerId/erase` и `…/privacy/clinic/:documentId/erase` с `{key, version, reason}`. Персональные поля, обращения, заметки CRM, исходные строки импорта, сообщения и коды привязки очищаются; связи с внешними контактами помечаются удалёнными, чтобы синхронизация не вернула данные; карточка блокируется (`SUBJECT_ERASED`). Заказы и деньги остаются связаны; имя контрагента в денежном журнале сохраняется как бухгалтерская запись (срок хранения по закону — решение заказчика). Журнал запросов без удалённых значений: `GET …/privacy/requests`.
- Экспорт организации: владелец — `GET organizations/:id/export` (до 50 000 строк, без двоичных файлов, с аудитом); оператор — `npm run org:export -- --org <id> [--binaries]` в `.data/exports` (файл 0600). Хеши паролей/токенов/кодов и зашифрованные реквизиты не выгружаются.

### Неопределённый расход AI после ошибки

`assistant_budget_reservations.actual_tokens IS NULL` сохраняет полный резерв после тайм-аута или краха. Не удалять такие строки и не увеличивать бюджет автоматически. Сверить вызов и фактический расход с кабинетом провайдера; при отсутствии доказательства оставить резерв. `breached=true` требует разбирательства с моделью/счётчиком перед разблокировкой. В текущей версии нет пользовательской команды автоматического списания/освобождения таких резервов; операторское исправление проводится отдельно с резервной копией и протоколом, без секретов в отчёте.


## T056: бесплатная локальная демонстрация (16.10.2026)

Настройка и условия — [AI_PROVIDERS.md](AI_PROVIDERS.md). В `.env.local`: `ASSISTANT_PROVIDER=free`, `ASSISTANT_SYNTHETIC_DATA=1`, серверные `GEMINI_API_KEY` и `OPENROUTER_API_KEY`. `npm run dev` включает локальные флаги. Ключи не в Git; на другой машине вводятся отдельно. `ASSISTANT_PROVIDER=disabled` — выключатель. Для shared/production режима synthetic opt-in не использовать. Старый раздел Anthropic выше остаётся отдельным вариантом, он не включается цепочкой бесплатных моделей.

При 429/недоступности приложение пробует запасной настроенный бесплатный адаптер в пределах общего таймаута. Если оба отказали, показывает ошибку; не подставляет выдуманный ответ и не переключает на платный тариф. Неизвестные исходы сохраняют резерв бюджета. Сверять их оператором; не обнулять остаток для обхода ограничений. Метаданные OpenRouter во время проверки сообщали used=0 даже после генераций: это не надёжный счётчик оставшихся запросов демонстрации.

## Демо, локальный голос и детектор людей (16.10.2026)

Демо на 3–5 минут: docs/DEMO_SCENARIOS.md (`db:seed:business` → `demo:prepare` → `build` → перед показом `demo:reset` и `preview`; проверка пути — `demo:rehearse`).

Голос локально (T056), подробности — docs/LOCAL_MODELS.md:

1. `npm run speech:model` — один раз скачивает Whisper large-v3-turbo ONNX 8-bit (≈ 1,3 ГБ) в `.data/models`. За корпоративным прокси: `NODE_USE_ENV_PROXY=1` (PowerShell: `$env:NODE_USE_ENV_PROXY=1`).
2. `.env.local`: `SPEECH_PROVIDER=local` (необязательно `SPEECH_MODEL`, `SPEECH_DTYPE=q8`, `SPEECH_MODEL_DIR`). Перезапустить `npm run dev`/`preview`.
3. «Помощник → Состояние помощника и настройки» → «Разрешить голос». При открытии помощника модель начинает загружаться (≈ 30 с на 4 ядрах); первая запись дождётся загрузки.
4. Проверка движка на открытых записях: `npm run speech:eval -- --n 30` (FLEURS, CC BY 4.0). Проверка на ваших разрешённых записях деловых фраз: `npm run voice:check -- --manifest <файл>` (docs/LIVE_ACCEPTANCE.md T056).
5. Выключить: убрать `SPEECH_PROVIDER` или снять «Разрешить голос». Процесс модели выгружается сам через 15 минут простоя и при остановке сервера.

Детектор людей (T057) на устройстве обработки возле камеры:

1. `npm run video:model` (RF-DETR Nano COCO, ≈ 108 МБ; `-- rfdetr-n rfdetr-s dfine-s` — несколько). D-FINE-N снят (не находил людей, docs/LOCAL_MODELS.md). Скорость на устройстве: `npm run video:bench`. Проверка камеры без приложения: `npm run video:check -- --webcam "video=<камера>"` (Windows) — посекундно люди и диагноз звена; инструкция docs/CAMERA_WINDOWS.md.
2. Обработчик: `npm run video:processor -- --server … --source … --rtsp [--detector rfdetr-n] [--fps 5] [--no-preview]`; запись как живая камера для показа: `--file shop.mp4 --loop`. Отказ сервера (например, перевыпущенный токен) останавливает обработчик и освобождает камеру с объяснением; `Ctrl+C` — штатная остановка. Классический режим — только явно: `--detector motion`. Без модели обработчик останавливается с подсказкой.
3. Сравнение режимов на ваших размеченных записях: `npm run video:eval-recorded -- --manifest <файл>`; статус детектора в приложении меняется только через «Разметка и оценка».
